# 稳定性策略

在 proptest 的不同版本之间你可以依赖什么、什么可能改变，以及每项改变如何公布。需求 RL15；由 golden 测试保证（Q7）；理由见 [ADR-0015](../../decisions/0015-stability-policy.md)。

**简而言之：** 在同一个次版本内（1.0.0、1.0.1、1.0.2……），同一种子产生相同的值、相同的探索过程和相同的反例。对其中任何一项的改变只会出现在新的次版本中，并且每一项都会列在 CHANGELOG 的 **Generation changes** 下。

## 这对你为什么重要

种子是一个"这次运行可以重放"的承诺。如果生成方式在补丁版本中改变，昨天从 CI 失败中复制的 `PROPTEST_SEED`，在一次无害的依赖更新之后，今天就可能重放出别的东西。你自己那些固定了种子的回归测试（`initSettings(seed = 42)`）会在你的代码毫无改动的情况下开始检查不同的输入。

相反的承诺——"值永远不变"——会冻结这个库：更好的边界用例、更快的生成器和更聪明的收缩都会改变值。本策略取其中间：允许改变，但只在你选择跨越的版本边界上发生，并且总会公布。

## 同一次版本内保持不变的内容

在 proptest 版本相同（含补丁版本）、测试代码相同、设置相同的前提下：

| 内容 | 涵盖 |
|---|---|
| **生成的值** | 每个内置生成器（所有支持类型的 `x in T`、推导出的对象、case object、`distinct`、`ref`、容器）、每个组合子，以及你自己的生成器所用的抽取原语（`drawInt`、`drawBool`、`drawIndex`、`drawFloat`……） |
| **运行过程** | 运行种子如何变成每个属性的种子（来自其 `name`）、规模在运行中如何增长、边界偏好、挖掘出的常量和 `near` 提示、swarm testing、丢弃多少用例 |
| **有状态序列** | 运行哪些命令、以什么顺序、带什么参数 |
| **收缩** | 收缩器走过的路径，以及为每个找到的失败报告的最小反例 |
| **失败数据库** | 其文件格式（`proptest-db 1`）以及条目的键 |
| **JSON 报告** | `format` 1 中每个字段的含义 |

这一点在 CI 测试的每个平台和构建上都成立：Linux、macOS 和 Windows；debug 和 release；`--mm:orc` 和 `--mm:arc`；线程开和关；Nim 2.2.4（Nim devel 也会测试，但作为允许失败的项：编译器的改动可能在任何版本公布之前就破坏它）。随机生成器和哈希是库自己的，并用参考向量校验，所以不依赖标准库的 `random` 或 `hash`，它们可能在 Nim 版本之间变化。

### "相同的测试代码"指什么

你的代码决定了部分生成内容，所以即使库版本和种子都相同，你的某些修改也会改变值：

- **移动属性。** 它的默认名称是 `file:line`，而它的种子来自名称。给它一个 `name`，代码行移动时种子就能保持不变。
- **测试文件中的整数字面量。** 它们会被作为边界值提议（`mineConstants`）。在文件中添加一个字面量，可能会改变该文件中其他属性生成的内容。`mineConstants = false` 可以让一个属性不受其文件影响。
- **你自己的生成器**以及它们抽取的顺序。
- **影响输入的设置：** `cases`、`maxSize`、`edgeBias`、`maxDepth`、`maxSteps`、`swarm`、`mineConstants`，包括来自环境变量的（`PROPTEST_CASES`）。

[CONFIGURATION.md](CONFIGURATION.md#what-a-replay-needs) 列出了重放所需的条件。

## 任何版本都可能改变的内容

以下内容不在保证范围内：在测试中依赖它们会让测试变得脆弱。

- **文本报告**：措辞、布局、打印哪些统计和警告。请改为解析 [JSON 报告](README.md#json-report-for-ci)。
- **值的打印方式**（`show`、`showCode`），当改动使其更清晰或更正确时。旧版本打印的 `replayCommands` 块仍是合法的 Nim 代码，但新版本可能会以不同方式打印它。
- **健康检查和警告**：新的检查、不同的阈值。
- **任何依赖时间的东西**：`deadline`、`timeBudget`、`shrinkTimeBudget`、慢生成检查。更快的机器在同一时间预算内会运行更多用例。
- **性能**：达到同一反例所需的收缩执行次数可能下降（在同一次版本内，反例本身保持不变）。
- **新 API**：新的生成器、组合子、设置、`PropertyResult` 中的字段，以及 JSON 报告中的新字段。添加字段永远不会改变 `format`。

## 改动如何公布

每个版本的 CHANGELOG 条目按类别对改动分组：

| 标题 | 包含 | 允许出现在 |
|---|---|---|
| **Added**、**Fixed**、**Changed** | 新 API、bug 修复、报告或文档的改动 | 任何版本 |
| **Generation changes** | [保持不变的内容](#what-stays-the-same-within-a-minor-version)中的任何一项：值、探索、收缩、文件格式 | 次版本（x.y.0） |
| **Breaking** | 让代码无法编译或改变含义的 API 改动 | 主版本（x.0.0） |

**Generation changes** 条目会说明改变了什么、影响哪些生成器或设置，以及保存的种子和失败数据库条目是否仍能重放。生成方式的改动会成批发布：多项改动一起进入一个次版本，这样种子只会失效一次，而不是每次改进都失效。

**Breaking** 的 API 改动在可能的情况下，会先在至少一个次版本中提供旧 API 的 `{.deprecated.}` 版本，并附带指明替代品的消息。

会改变值的 bug 修复（某个生成器本应能产生却从未产生某些值）仍属于生成方式的改动：它会等到下一个次版本，除非该 bug 让库无法使用，这种情况下补丁版本会在 **Generation changes** 下说明。

## 升级时

- **补丁版本（1.0.1 → 1.0.2）：** 什么都不用做。种子、固定的测试和保存的失败都继续有效。
- **次版本（1.0 → 1.1）：** 阅读 **Generation changes**。旧版本打印的种子会重放出不同的输入：请用旧版本重放旧的 CI 失败。带固定 `seed` 的属性现在会检查不同的输入，这通常没问题；检查一下那些断言某个种子产生的确切值的测试。失败数据库什么都不用做：不再适配生成器的条目会被丢弃，现在通过的条目会在三次运行后被遗忘，真实的 bug 仍然会失败。
- **要永久保留某个特定输入**，不要依赖种子：用 `example(...)` 把它写下来，或者对状态机，把 `replayCommands` 块粘贴进测试。这些完全不依赖生成方式。

## 如何保证

- **Golden snapshot**（`tests/t_golden.nim`、`tests/golden/snapshot.txt`）：让 51 个属性跑完整个流程（每种类型和组合子、推导类型、挖掘的常量、边界偏好、规模、swarm、若干参考 bug 的收缩、一个状态机、失败数据库文件），并把每个生成值和每个收缩候选的哈希，连同可读的样本，与已提交的快照进行比较。CI 在上述每个平台和构建模式下都会运行它。
- **参考向量**（`tests/t_prng.nim`）：随机生成器和哈希对照其作者的参考代码以及 FNV-1a 官方向量。
- **流程**：快照测试失败时，消息会说明这一点。有意的改动通过 `nimble golden` 记录，并在同一个提交中于 CHANGELOG 的 **Generation changes** 下添加条目；其他任何情况都是需要修复的回归。

快照测试是补丁版本兑现承诺的证据：如果它在发布提交上通过，该版本生成的内容就与同一次版本中的前一个版本完全相同。
