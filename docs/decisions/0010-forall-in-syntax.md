# ADR-0010: `forAll(x in source)` syntax

- Status: Accepted
- Date: 2026-11-19
- Requirements: A1, G3, PF5

## Context

The first sketch used `forAll(xs: seq[int])` for type-inferred variables and `forAll(n = gen)` for generator values. The first form cannot work: when every argument of a call has the shape `name: value`, the Nim parser builds an **object constructor** (`nnkObjConstr`), and semantic checking fails with "type expected" before any macro is invoked. There is no hook to recover from it.

## Decision

Every variable is declared as `name in source`:

- `xs in seq[int]`: the source is a type, generated by `arbitrary(src, T)`;
- `n in ints(0, 100)` or `n in evens`: the source is a `Gen[T]` value.

The macro does not need to know which one it got. It emits `let s = hoist(source)` once per property and `drawFrom(src, s)` per case:

- `hoist` is a template for `typedesc` (it returns a zero-size `TypeGen[T]` marker) and a proc for `Gen[T]` (it returns the value);
- `drawFrom` is overloaded: for `TypeGen[T]` it calls `arbitrary(src, T)` directly (no closure, PF5); for `Gen[T]` it calls the closure.

Any other argument is taken as a `Settings` expression. `name: T` and `name = g` are rejected with a message that shows the right form.

## Consequences

- Reads like the mathematical ∀x ∈ S, and one form covers types and generators.
- Sources are evaluated once per property, so generator values are not rebuilt per case.
- User overloads of `arbitrary` are found at the call site (`mixin`), so custom types work with `x in MyType`.

## Evidence

`examples/quickstart.nim` (both forms); compile-error test for the rejected forms (pending with the test suite).
